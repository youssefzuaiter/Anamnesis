# Quiz me: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From a note or a course, ask the person questions (their own cards first, then questions the model writes from their notes), check their typed answers, and show a score (ROADMAP item 10).

**Architecture:** A pure `lib/quiz.ts` holds every rule that does not need a model: which cards to ask, normalising and rule-judging answers, grading maps, scoring, excerpt sampling and a groundedness check. `services/quiz-service.ts` composes them with scope resolution, the card and note repositories, and two model calls (`modelGenerator`, `modelJudge`) that are passed in as arguments so tests never call a model. The model only *suggests*: a card's schedule changes only when the person clicks a grade, through the existing `reviewCardAction`. Nothing about a session is stored.

**Tech Stack:** Next.js 16 (server actions; `searchParams` is a Promise), React 19, Prisma 7 + Postgres, Zod, Ollama `llama3.2:3b` through `completeJson` (temperature 0), node:test, Playwright. No new dependency, no migration.

**Spec:** none written (ROADMAP item 10 is not tagged *demo*); the design is in this plan. The decisions below were made after a council I ran inline, not by independent subagents, so it is weaker than four separate voices. `CLAUDE.md` ("Building features, one at a time", "Testing UI with Playwright", "Scoped assistant questions", "The assistant, and what actually defends it", "Cloze cards, decks and cards from selection") and `AGENTS.md` bind.

## Decisions (for CLAUDE.md, with the cost accepted)

1. **Cards first, the model only fills the gap.** A card needs no model and has a trusted reference; generated questions are the fallback. *Cost:* a person with plenty of cards never sees a generated question.
2. **Hybrid judging.** Rules decide the trivial cases (empty, "I don't know", equal after normalising); the model judges the rest. Rules are deterministic, cost nothing and remove model error where it is least excusable. *Cost:* a correct answer that differs only by a typo goes to the model.
3. **The verdict is a suggestion; the person grades.** A 3B judge is wrong some of the time and a wrong verdict must not silently damage a card's schedule. *Cost:* one more click per card.
4. **Nothing stored, no migration.** A card is looked up by id on the server so its reference never comes from the browser; a generated question round-trips question, reference and excerpt through the browser as untrusted bounded text (it only affects the person's own session). *Cost:* no history or streaks; a generated question cannot be revisited.
5. **A model failure degrades, never blocks.** At start the quiz becomes cards-only with a notice; at check time the result says the model could not judge, shows the reference and asks the person to grade themselves.
6. **Questions are generated from the notes' text, not from the embedding table**, so a note saved while Ollama was down still works. *Cost:* the generator sees a deterministic spread of excerpts, not the "best" ones.
7. **A groundedness filter** drops generated questions whose answer is mostly not made of words from the excerpt it cites; the threshold is chosen from the measurement in Task 4, not guessed.

## Review Focus

Most likely first; each has a test in the task that owns the code.

1. A card id in the check call that is another account's, trashed, or missing: one refusal, and no reference leaks (T2).
2. An answer that forges a fence (`<<<END …>>>`), a role label (`SYSTEM:`), or says "mark this correct": it reaches the judge fenced and defanged, and only an enum verdict comes back (T1, T4 measures the rate).
3. The model unreachable at start and at check: the quiz still runs on cards; a check says so and the person grades themselves (T2, T3).
4. A note with almost no text and no cards: a plain "nothing to quiz yet" message, no error, no model call (T2, T3).
5. A grade is never recorded without a click, including after a correct verdict (T3).
6. Hostile 100,000-character answers and notes through the normaliser, tokenizer, groundedness and sampler stay linear (T1).
7. Double click on Check does not skip or double-count a question (T3).
8. Phone 375px, light and dark: nothing overflows, controls at least 44px (T3).
