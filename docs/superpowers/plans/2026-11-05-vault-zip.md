# Markdown vault export and import Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `GET /api/export/vault` streams a zip of one `.md` file per live note (with `[[links]]` intact and the note's attachments beside them) that Obsidian opens, and `POST /api/import/vault` restores from such a zip (or any Obsidian vault zip) after a preview, never duplicating on a second run.

**Architecture:** A pure zip layer on Node built-ins (`lib/zip.ts`: a writer that emits one entry at a time, a reader that validates before it inflates); pure vault rules (`lib/vault.ts` names and front matter out, `lib/vault-import.ts` parse, sniff and plan in); one service (`services/vault-service.ts`) that reads through scoped repositories on the way out and writes only through `noteService.createNote` and the attachment store on the way in; two route handlers (a raw zip body is not a Server Action: the action body limit is 15 MB and a vault with PDFs is bigger); a preview-then-confirm form on `/notes/import` and a link on Settings.

**Tech Stack:** Next 16 route handlers (Web `ReadableStream`), Prisma 7, `node:zlib` (`deflateRaw`, `inflateRaw` with `maxOutputLength`, `crc32`), Zod, Vitest-style unit/integration tiers already in the repo, Playwright. No new dependency, no migration.

**Spec:** ROADMAP item 12 (`ROADMAP.md`): "Markdown vault export and import (M, depends on 11). A zip of `.md` files with `[[links]]` and attachments that Obsidian opens, and a way to restore from it." No written spec beyond that; the Decisions below are the design. Read with them: CLAUDE.md "Data export", "File attachments", "Backlinks use `[[Note title]]`", "`/notes/import`".

## Global Constraints

- No new dependency, no migration, free local stack. Node 24 (`zlib.crc32` exists; Dockerfile and CI are Node 24).
- Every query scoped by the session's `userId` from `requireUserId()`; nothing in the uploaded file is an id, an owner or a path that is trusted. Notes are written only through `noteService.createNote`; files only through `putAttachment` (generated `{uuid}.{ext}` key). **No entry name ever reaches the filesystem.**
- Limits (constants in `lib/zip.ts` and `lib/vault.ts`, one place each): zip body 100 MiB (`104857600`); entries 20,000; one entry 10 MiB (`10485760`) and a `.md` entry 512 KiB; total declared uncompressed 400 MiB (`419430400`); at most 500 notes created per import run (a second run continues, because a run never duplicates); at most 20 attachments per note; at most 12 tags of 50 characters; title 200; note text `MAX_NOTE_LENGTH` (100,000) after LF normalisation.
- zip32 only (no zip64), no encryption, methods 0 and 8 only. The writer throws before it could wrap an offset; a stream that hit that limit is never a valid zip (no end record).
- The vault holds notes and their attachments only; the file says so (`.anamnesis/manifest.json`, the Settings text). Tasks, events, cards, courses, grades and the rest are in the JSON export and `ops/backup.sh`.
- `noteContent` (`lib/note-text.ts`) is the only length rule for note text. Titles are compared with `normalizeTitle` (`lib/wiki-links.ts`).
- Commit trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; never `git add -A` (`AGENTS.md` is rewritten by `next dev` and stays uncommitted). CPU budget: targeted specs only at `nice -n 10`, Ollama off, one `pnpm build`, "CI runs the rest".

## Decisions (made while shaping; the council was run by me inline, so weaker than four independent voices)

1. **Zip: build, not adopt.** Checked the registry (fflate 0.8.3, yauzl 3.4.0, archiver 8, jszip 3.10.2, adm-zip 0.6.1, zip-stream 7.0.5): all maintained, MIT (jszip dual). The rule is no new dependency, the hardening that matters (declared sizes capped before any inflate, output bounded to the declared size, CRC checked, zip64 and encryption refused) is ours with any of them, and `fflate` is about 800 KB for about 250 lines of need. **Cost if wrong:** a parser bug on an unusual real-world zip; mitigated by reading zips made by macOS `zip` and `ditto` and by `unzip -t` on ours. Fallback if it proves fragile: `fflate`.
2. **Layout: flat.** `<Title>.md` at the root, files in `attachments/`, `.anamnesis/manifest.json`. Obsidian resolves `[[Title]]` by file name anywhere, so folders add nothing, and a flat vault needs one name-uniqueness rule. Course and project are front matter, not folders.
3. **File name = title, so `[[Title]]` works in Obsidian.** Characters Obsidian cannot link (`\ / : * ? " < > | # ^ [ ]`, controls) become `-`; at most 180 UTF-8 bytes; names unique case-insensitively across notes **and** attachments; the note the app's own link resolution would pick (most recently updated) keeps the plain name, the others get ` (2)`, ` (3)`. NFC. The true title is front matter, so nothing is lost by the sanitising. **Known limit:** a link to a title that had to be sanitised does not resolve in Obsidian (it still does in the app).
4. **Attachments are a front-matter property of links, the note text is never rewritten.** `attachments: ["[[diagram.png]]"]` is a link property in Obsidian, costs the body nothing, and the text round-trips byte for byte. The app's note text never referenced attachments (they are rows), so nothing in the body points at them.
5. **Front matter is JSON-valued YAML** (`title`, `tags`, `favorite`, `course` (the course code), `project` (the title), `attachments`, `created`, `updated`, and `anamnesis: 1`). JSON strings and flow lists are valid YAML, so Obsidian reads them and the importer needs no YAML parser, only a small tolerant reader for foreign files. **No ids are exported**, so there is none to trust on the way back.
6. **Identity on import is content, not an id: a note is "already there" when the account has a live note with the same title family and the same text.** The family is the normalised title with a trailing ` (imported)` / ` (imported N)` removed; the text is compared by SHA-256 of the LF-normalised content (computed in SQL for existing notes, in JS for incoming). So importing twice creates nothing the second time, a changed note comes in beside the original rather than over it, and no id is trusted. **A note whose title is already used by a different note in the account comes in as `Title (imported)`** (then `(imported 2)`), so it cannot take over `[[Title]]` for the note you already have (link resolution prefers the most recently updated). Two notes of the same title *inside the file* keep their titles (the app allows duplicates). Never overwrites, never deletes. **Cost accepted:** a link in an imported note to a renamed note points at the note already in the account; two simultaneous imports can each create a copy (nothing in the database forbids it, as with daily notes).
7. **Preview, then apply, from the same code.** One function runs the whole pipeline with `apply: false` or `true`; the form keeps the `File` in the browser and posts it twice (preview, then confirm); the server stores nothing between the two and re-derives everything on apply. **Cost:** the file is uploaded twice (local machine).
8. **Course and project on import are matched by name among the caller's live ones, never created.** Course by code (ambiguous or unknown: none), project by title. A note keeps its place when its course still exists and loses it (reported) when not.
9. **Foreign vaults are accepted, with losses reported.** Title = file name (so links keep working), not the first heading (the older Markdown importer's rule); front matter keys other than tags are dropped and counted; embedded images in the body are not attached (only the `attachments` property of our own files is); notes without our marker get the `imported` tag, ours do not (a restore should not tag everything).
10. **Zip entries are hostile data.** Unsafe names (`..` segment, absolute, NUL or control characters, `__MACOSX/`, `._*`, `.obsidian/`, `.trash/`, `.anamnesis/`), symlinks, encrypted, unsupported or oversized entries and duplicate names are skipped with a counted reason; a structurally bad archive is refused whole. Attachment bytes must match their extension's magic bytes (text types: valid UTF-8 without NUL) before they are stored.

## Review Focus

- **A zip that lies about sizes, or is a bomb** (1 GiB of zeros in 1 MB, a declared size smaller than the real one, 1,000 entries each at the cap): refused or skipped before memory or time is spent; never an out-of-memory.
- **A title clash with a different note already in the account**: the existing note keeps the link; a second import adds nothing; a vault with notes of the same title inside it restores with both.
- **Names Obsidian or a filesystem cannot take**: `CON`, trailing dots, `a/b?c`, a 200-character Turkish title (2 bytes per letter), `Note.md` and `note.md`, NFD `ş` from a Mac, an attachment called `Meeting.md` next to a note called `Meeting`.
- **A 100,000-character title, front matter, tag list or link run** (the lesson of items 7 to 11: measure, do not read): linear, a few milliseconds.
- **A vault bigger than one run or than zip32**: 501 new notes import 500 and say how many are left; the export refuses before the first byte when it cannot fit and aborts (no end record) rather than wrap an offset.

### Task 1: The zip layer

**Files:**
- Create: `src/lib/zip.ts`, `tests/unit/zip.test.ts`, `tests/unit/fixtures/` (two tiny real-world zips as base64 text: one from macOS `zip`, one from `ditto -c -k`)

**Interfaces:**
- Produces:
  - `const ZIP_LIMITS = { maxZipBytes: 104857600, maxEntries: 20000, maxEntryBytes: 10485760, maxTotalBytes: 419430400 }`; `type ZipLimits = { [K in keyof typeof ZIP_LIMITS]: number }`.
  - `class ZipError extends Error { readonly code: "too-large" | "invalid" | "unsupported" | "corrupt" }`.
  - `class ZipWriter { constructor(options?: { maxOffset?: number }); add(entry: { name: string; data: Uint8Array; modified: Date; store?: boolean }): Promise<Buffer>; finish(): Buffer }` — `add` returns the local header plus data of one entry and records it; `finish` returns the central directory and end record. Names are UTF-8 with bit 11 set; DOS time from UTC components clamped to 1980 to 2107; deflate unless `store` or deflate does not shrink; throws `ZipError("too-large")` if an offset, a size or the entry count would pass zip32.
  - `type ZipEntry = { name: string; size: number; compressedSize: number; crc: number; method: number; modified: Date; directory: boolean; symlink: boolean; unsupported: string | null }`.
  - `function openZip(bytes: Uint8Array, limits?: Partial<ZipLimits>): { entries: ZipEntry[]; read(entry: ZipEntry): Promise<Buffer> }` — structural problems throw `ZipError` at open (shorter than an end record, no end record, comment length that does not reach the end, disk numbers or entry counts that disagree, zip64 markers or locator, more entries than `maxEntries` before any is parsed, central directory outside the file or past the end record, a record that runs off the directory, bad record signature, declared sizes of readable entries summing over `maxTotalBytes`, bytes over `maxZipBytes`). Per entry: `unsupported` is set (reason string) for encryption, a method other than 0 or 8, a zip64 size, or `size > maxEntryBytes` (these do not count toward the total). `read` checks the local header (signature, data inside the file and before the directory), inflates with `maxOutputLength` equal to the declared size, then checks exact length and CRC, else `ZipError("corrupt")`; refuses an `unsupported` entry; an empty entry is returned without inflating.
