# Error and uptime alerts Implementation Plan

**Goal:** When the app is down, its reminders have stalled, ntfy is down, a nightly backup did not happen, or the off-site copies have stopped arriving, the owner's phone is told once, and told again when it recovers. A failed backup or verify says so at the moment it fails.

**Architecture:** Reuse the ntfy server from item 19. Alerts go to a separate topic, `ALERT_TOPIC` (`anamnesis-ops-<random>`), which the existing ACL already lets the app publish to (`anamnesis:anamnesis-*:wo`) and the phone read (`phone:anamnesis-*:ro`), so no ACL change. Two producers: `ops/watch.mjs`, run by launchd every five minutes, checks what cannot report its own failure (the app is down, the scheduler has stalled, no backup happened, ntfy is down); and the failing scripts (`backup.sh`, `verify-backup.sh`, `offsite.sh`) send one alert through the same publisher when they exit non-zero. The rules are a pure function with an explicit two-run threshold and a state file, so a single blip is not an alert and a long outage is one message, not one every five minutes.

**Spec:** ROADMAP item 29: "Error and uptime alerts (S, ops). Reuse whatever 19 chose (ntfy: the app token may publish to `anamnesis-*`)."

**Money:** none. Everything runs on this Mac and the existing ntfy server. **Limit, said plainly:** if the Mac is off or asleep, nothing can alert, because the watcher lives on it. Watching from outside (a free external monitor, or a paid service) would need the public address of the app; that is not built.

## Global Constraints
- No new dependency; `ops/watch.mjs` uses Node built-ins only, like `smoke.mjs` and `retention.mjs`.
- The watcher never sends the app's token, the reply body, or an address in a message; errors are sanitised to "answered 401", "timed out", "did not answer".
- An alert is sent on the second consecutive failing run (ten minutes at the five-minute interval) and once when the check recovers after an alert. A failing check does not repeat until it recovers.
- No alert topic configured means: the watcher still runs and writes its state, and logs one line per change; nothing is sent. The alerts are optional, like reminders.
- Failure paths in the shell scripts never change their exit status or hide the original error; an alert that cannot be sent is a warning.
- Reads the env file without sourcing it (as `ops/lib.sh` does).

## Review Focus
1. A flapping check (fails, recovers, fails) must not produce a message per flip.
2. A token or an address leaking into the alert text or the log.
3. Not configured (no ntfy, no off-site folder) must not alert.
4. A backup failing for a reason the watcher cannot see (a stuck lock) still gets noticed, via the backup's own failure alert.
5. Clock: a backup stamp in UTC against a local clock.

### Task 1: `ops/watch.mjs` decision rules (pure) and tests.
`decide(previous, observations, now)` returns `{ state, alerts }`. Checks: `app` (health not ok), `reminders` (configured and last tick more than five minutes ago), `ntfy` (its health endpoint not ok), `backup` (no backup folder, or newest older than 26 hours), `offsite` (copies stale, only when configured).
### Task 2: publishing, reading the env file, the state file, `--notify`.
`publish` posts JSON to the ntfy root with the app token, like `src/lib/ntfy.ts`; `readEnv` parses KEY=VALUE without executing anything; the CLI `--notify <title> <body>` sends one message and exits 0 even when it cannot.
### Task 3: wire the failing jobs and launchd.
`backup.sh`, `verify-backup.sh` and `offsite.sh --check`/copy: non-zero exit sends one alert. `com.anamnesis.watch.plist.template` every 300 seconds; `install-launchd.sh` installs it. `ntfy-setup.sh` adds `ALERT_TOPIC` if missing.
### Task 4: tests (unit against a real local HTTP server for the publisher), mutation checks, rehearsal step, docs.
